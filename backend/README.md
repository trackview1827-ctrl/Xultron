# Xultron backend

Flask API backend for Xultron.

## Runtime

- Python 3.11 or newer is required.
- The backend uses `datetime.UTC` and is intentionally not advertised as Python 3.10 compatible.

## Validation

Run from this directory:

```bash
python -m compileall app tests
python -m pytest
```

## Native mobile authentication contract

Browser authentication remains the existing signed Flask session cookie plus
`X-CSRF-Token` flow. Native clients use opaque bearer credentials. A valid mobile
bearer may call the existing `/api/v1` APIs without browser CSRF headers. Supplying an
invalid `Authorization` header never falls back to a browser cookie.

### Token policy

- Access tokens are opaque `mat_...` bearer values with a 15-minute default lifetime.
- Refresh tokens are opaque `mrt_...` values with a 30-day absolute family lifetime.
- Only SHA-256 digests of both token types are stored. Tokens contain 256 bits of
  randomness generated by Python's `secrets` module.
- Every successful refresh consumes the presented token and returns a new refresh
  token. Reuse of a consumed token revokes the complete mobile session family,
  including every access and refresh token in it.
- Guest token-family expiry is capped by the guest account expiry.
- Defaults are configurable with `MOBILE_ACCESS_TOKEN_LIFETIME_SECONDS` and
  `MOBILE_REFRESH_TOKEN_LIFETIME_SECONDS`.

### Device object

All enrollment, login, and guest requests carry:

```json
{
  "installationId": "client-generated-random-id",
  "name": "Pixel 9",
  "type": "android",
  "appVersion": "1.0.0",
  "metadata": {"sdk": 35}
}
```

`installationId` is a stable random identifier generated by the app, not a hardware
identifier or authentication secret. A device is scoped to its user. Access and refresh
families are bound to the resulting device row.

### Endpoints

| Method and path | Authentication | Request | Result |
|---|---|---|---|
| `POST /api/v1/device-auth/enroll` | None, or guest Bearer for upgrade | `username`, `email`, `password`, `device` | Creates/upgrades the user and returns a token pair, user, and mobile session. |
| `POST /api/v1/device-auth/login` | None | `identifier`, `password`, `device` | Verifies credentials, registers/reactivates that user's device, and returns a token pair. |
| `POST /api/v1/device-auth/guest` | None | `device` | Creates an expiring guest user, device, and token pair. |
| `POST /api/v1/device-auth/refresh` | Refresh token in JSON, omit Bearer | `refreshToken` | Atomically consumes it and returns rotated access/refresh tokens. |
| `POST /api/v1/device-auth/logout` | Bearer, or refresh token in JSON | `{}` or `refreshToken` | Idempotently revokes that complete token family. |
| `POST /api/v1/device-auth/revoke` | Bearer | Exactly one of `sessionId`, `deviceId` | Revokes an owned family or every family for an owned device. |
| `GET /api/v1/device-auth/sessions` | Bearer | None | Lists only the authenticated user's mobile sessions and devices. |
| `POST /api/v1/devices/register` | Bearer | Device object | Idempotently updates the current session's bound device. A different installation is rejected. |

Token responses have this shape:

```json
{
  "tokenType": "Bearer",
  "accessToken": "mat_...",
  "accessExpiresAt": "2026-08-31T09:15:00Z",
  "expiresIn": 899,
  "refreshToken": "mrt_...",
  "refreshExpiresAt": "2026-09-30T09:00:00Z",
  "user": {},
  "session": {"id": "mas_...", "device": {}, "current": true}
}
```

Errors use the existing `{ "error": { "code", "message", "retryable", "requestId" } }`
envelope. Security-relevant codes include `access_token_expired`,
`access_token_revoked`, `refresh_token_expired`, `refresh_token_revoked`,
`refresh_reuse_detected`, `device_mismatch`, and `forbidden`.

### Threat model notes

- **Stolen access token:** bounded by the short lifetime and invalidated on family or
  device revoke.
- **Stolen refresh token:** single-use rotation limits its window. Replay revokes the
  family and emits a persistent, secret-free auth event plus a warning log.
- **Database disclosure:** plaintext bearer credentials are never persisted.
- **Cross-user IDOR:** session/device revocation and existing resources verify the
  authenticated user before access.
- **Credential confusion:** explicit Bearer credentials take precedence and fail closed;
  they cannot silently fall back to a different cookie identity.
- **Browser regression/CSRF:** cookie requests retain same-origin and CSRF enforcement.
  CSRF is skipped only for valid bearer requests and the credential-only native auth
  endpoints, which do not authenticate from ambient cookies.
